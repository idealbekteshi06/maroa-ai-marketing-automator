## 1. P0 — Multi-business `.maybeSingle()` class (regression of PR #4; **5 sites**, cascading)

> **Count correction (post-publication re-sweep):** the first pass reported **3** sites and called them exhaustive. A later grep sweep (`.eq("user_id", …)` + `.maybeSingle()`/`.single()` across all of `src/`) found **two more**: `SocialCallback.tsx:42-46` (Meta OAuth connect fails for multi-business accounts) and `SignUp.tsx:97-101` (post-signup business read-back → instant-content webhook skipped). All **5** are fixed via the shared `pickPrimaryBusiness()` helper; a regression grep now asserts **zero** non-list single-reads on `user_id` remain anywhere in `src/`. This correction is itself a finding: "exhaustive" claims must be backed by a mechanical sweep, not inspection.

A user can legitimately have **more than one `businesses` row** (the account that originally reported this has two). PostgREST's `maybeSingle()` **errors on a multi-row result**. The fix merged in PR #4 (`0fdd97b`) replaced this with an ordered multi-row select; the April-17 restore (`03a7de6`) wiped it. The pattern existed at five sites with a cascade:

**1a. `src/pages/Login.tsx:86-97` — hard login failure (worst).**
```ts
.from("businesses").select("onboarding_complete").eq("user_id", sessionUser.id).maybeSingle()
…
if (bizError) throw bizError;            // ← multi-row ⇒ bizError set ⇒ throw
```
Email/password sign-in succeeds at the auth layer, then this throws → `toast.error` → **the user never reaches `/dashboard`**. A multi-business user is locked out of password login. (Google OAuth path skips this and limps to the dashboard, where 1b takes over.)

**1b. `src/contexts/AuthContext.tsx:39-45` — `businessId` never set.**
```ts
.eq("user_id", userId).maybeSingle();
if (!mountedRef.current) return;
if (error) { return; }                   // ← silent; businessId stays null forever
```
Consequences ripple app-wide: `DashboardContent.handleGenerateNow` (line 112 `if (!businessId) return;`), `DashboardOverview.handleQuickAction` (line ~280 `if (!businessId) return;`), and every `enabled`-style guard become **silent no-op buttons** — the original "buttons do nothing" complaint.

**1c. `src/components/dashboard/DashboardOverview.tsx:175-176` — overview error state.**
The fallback branch (`businessId` null — guaranteed by 1b) runs `.eq("user_id", user.id).maybeSingle()` → error → `setError("Something went wrong…")` on the Home tab.

**1d. Duplicate-business hazard (same function).** `AuthContext.tsx:47-50`: the insert-new-business branch (`else if (user)`) is gated only on falsy `data`, not on a confirmed zero-row read. PR #4 hardened this to `rows.length === 0`; the hardening is gone. Any path that yields falsy `data` without `error` re-opens duplicate-row creation — which is what *created* the second business row on the affected account in the first place.

**Fix (port of the already-reviewed PR #4 logic, now needed in 3 files):**
```ts
const { data, error } = await supabase.from("businesses")
  .select("id, onboarding_complete").eq("user_id", userId)
  .order("onboarding_complete", { ascending: false })
  .order("created_at", { ascending: true });
const rows = data ?? [];
const chosen = rows.find(b => b.onboarding_complete) ?? rows[0] ?? null;
// insert-new-business ONLY when !error && rows.length === 0
```
Longer-term: add a "primary business" marker (or de-dupe + partial unique index) in the DB — backend task, see §9.

## 2. P1 — Functional and honesty regressions

**2a. `PendingApprovals.tsx:39-54` — selects non-existent `caption` column, zero error handling.**
`.select("id, platform, caption, content_theme, quality_score")` on `generated_content`. Every other consumer of this table uses per-platform columns (`instagram_caption`, `facebook_post` — e.g. `DashboardPublish.tsx:136`, `PostPreviewModal.tsx`), and the bare-`caption` select is the exact query class that produced the user-observed PostgREST 400s. The result is destructured as `const { data } = …` with **no error check**, then `data || []` → the Home-tab approvals widget **silently renders empty and hides itself** (`visible=false` effect at lines 76-83) while real pending content exists. Fix: select the real columns, derive the preview (`instagram_caption || facebook_post || content_theme`), and surface `error` with a toast. *(Schema caveat: the external DB schema isn't in-repo; confidence is high from in-repo consistency + observed 400s — verify with one live query.)*

**2b. `DashboardContent.tsx:111-126` — "Generate Now" fake progress + unconditional success (regression).**
```ts
if (!businessId) return;                       // silent no-op (see §1b)
apiFireAndForget("/webhook/instant-content", …) // never throws, result ignored
for (const msg of msgs) { await … 5000 … }      // 25s of theater
toast.success(SUCCESS_MESSAGES.GENERATED);      // fires EVEN IF the call failed
```
The previously-shipped flow (`generateContentNow` → `/api/content/generate`, real errors, real theme in the toast — commit `58e027e`, wired in the pre-restore tree) is gone; `generateContentNow` no longer exists in `apiClient.ts`. Users on broken accounts see "✓ generated" forever with nothing appearing. Same unconditional-optimism pattern in `DashboardOverview.handleQuickAction` is acceptable-ish (it awaits and catches), but `instant-content` here does not even await.

**2c. Fake `Math.random()` metrics presented as real data (3 pages).**
`AdOptimization.tsx:99-108` (chart from `Math.random()`, hardcoded deltas `+12.4%`, `2.8x`, `-8.7%`; its own TODO admits "wire to real API"), `EmailLifecycle.tsx:105-107`, `BudgetROI.tsx:76-77`. These render as live performance numbers with no "demo" labeling. Fix: wire to real endpoints or add an explicit "Sample data" badge.

**2d. Unshipped "22 countries / 17 languages" claim restored.**
`index.html:7,10` and `src/pages/Index.tsx:170`. Commit `eb4fd2d` deliberately removed this claim ("drop unshipped 17-languages claim"); the restore brought it back into the meta description, OG description, and hero copy.

**2e. The unmerged fix branch is now unlandable.**
`origin/claude/nice-shannon-ad3170` (commit `9125fd7`: caption-400 fixes + silent-failure toasts) is still open but was written for the pre-restore tree — its target files were deleted/replaced. Its *intent* must be re-implemented on this tree (2a above is the new location of the same bug). Recommend closing the branch with a note, to stop it being merged into the wrong tree later.

## 4. P1 — Process/guardrail gaps (how regressions keep shipping)

- **No CI whatsoever** (`.github/` absent). Nothing runs tsc/eslint/build/tests on PRs; the April restore that wiped merged fixes sailed through unchecked.
- **Hooks build-gate wiped.** PR #7 added `eslint.hooks.config.js` + `prebuild` (`react-hooks/rules-of-hooks` as a build-failing error) after a real production #310 crash; `03a7de6` deleted it. This tree currently has 0 violations, but the protection is gone.
- **Type safety is mostly off:** `tsconfig` `strict: false`, `strictNullChecks: false`; no generated Supabase types — every `.select()` string is unchecked (the §2a bug class is invisible to tsc).
- **Tests: one placeholder** (`src/test/example.test.ts`). No test covers auth, the multi-business path, or any dashboard data flow.
- **Restore-by-replacement workflow:** `03a7de6` replaced the tree wholesale instead of reverting/cherry-picking, which is exactly how `0fdd97b`'s and PR #7's merged fixes were silently lost. Future restores should be audited against a "load-bearing fixes" list (this document's §10 table is that list).

**Recommended minimum CI (1 file):** GitHub Actions running `npm ci && npx tsc --noEmit && npx eslint . --quiet && npm run build && npm test`, plus re-adding the hooks gate as `prebuild`.
